# 基于 GPU 架构的可扩展并行 Trace 性能分析工具中期考核报告 (草案)

## 一、 研究背景与动机 (Background & Motivation)

随着高性能计算 (HPC) 系统规模的持续扩大，应用程序的并发度急剧上升，用于性能诊断的 Trace 数据量呈指数级增长（通常达 GB 甚至 TB 级）。传统的串行或基于多核 CPU 的分析工具在面对海量数据时，受限于内存容量与计算扩展性，已逐渐成为性能分析的瓶颈。

Trace 分析的核心负载特征表现为：数据量极大，但单个事件的处理逻辑相对简单（如状态更新、时间戳比对），且数百万个事件之间具备高度的并行处理潜力。这属于典型的 **Data-Parallel** 任务。现有主流工具仍依赖擅长复杂逻辑控制的 CPU，而未能充分利用擅长海量数据并行 (SIMT) 的 GPU。因此，本研究致力于将 Trace 分析负载从 CPU 迁移至 GPU，以突破传统架构的吞吐量瓶颈。

## 二、 文献调研与现有工作 (Related Work)

目前的并行 Trace 分析工作主要集中在优化 CPU 端的负载均衡与通信开销，但并未根本解决算力供给端的局限性：

1. **Scalasca 与重放分析**：Scalasca 开创了并行重放分析的先河。每个分析进程读取本地 Trace 并重放 MPI 通信，计算 8 项等待状态指标（如 Late Sender, Barrier Wait 等）。其局限性在于极高的 CPU 资源消耗，并需要执行复杂的受控逻辑时钟 (CLC) 时间戳修正以消除节点间时钟偏移。
2. **TraceFlow 的交互感知分布 (2025)**：通过静态二进制分析提取通信骨架树 (CST)，将具有交互关系的事件分配至同一重放进程，从而消除重放期间的通信开销。尽管其在 512 个核心上实现了对 Scalasca 约 13.49 倍的加速，但其计算基础仍受限于 CPU 并发上限。本系统借鉴了其两阶段读取的思想。
3. **基于事件密度的并行化 (2019)**：Reumont-Locke 等人提出了基于数据包的混合划分方案，以平衡流与时间维度的负载。其独立处理后按时间顺序合并未知状态的思路，对本系统跨批次的 P2P 匹配具有概念上的指导意义。

## 三、 研究方法与系统设计 (Methodology & Architecture)

本研究的核心假设是：Trace 性能分析本质上属于高度数据并行 (Data-Parallel) 任务，其计算瓶颈在于海量简单逻辑的高吞吐处理，而非复杂控制流。因此，本研究摒弃了纯 CPU 的并行化思路，设计了 CPU-GPU 异构协同的分析管线。

### 3.1 传统 CPU 并行分析机制的局限性剖析()

在确定本系统架构前，有必要深入剖析现有基于 CPU 的并行 Trace 分析工作，其演进过程揭示了 CPU 架构在处理该类负载时的固有瓶颈：

1. **并行重放的扩展性危机**：早期的并行分析方法依赖于“并行重放” (Parallel Replay) 机制，即分析工具的进程数量与目标应用程序的进程数量保持 1:1 映射。这种方法在处理现代 HPC 系统（动辄数万至数十万个进程）时，会导致极其庞大的内存开销，且由于需要严格模拟原始程序的通信模式，进程间的同步开销往往抵消了并行化带来的收益。
2. **负载均衡与状态合并的矛盾**：为解决资源消耗问题，后续研究引入了基于有限状态机 (FSM) 的并行模型，并重点探索了数据划分策略。按流划分 (By Stream) 会导致严重的负载不均；按时间划分 (By Time) 虽然均衡了数据量，却切断了事件间的时序依赖。尽管混合划分 (Hybrid) 策略利用 Stream Packet Index 实现了工作负载的均衡分配，但多核 CPU 在处理跨流依赖时，需要进行大量昂贵的状态合并 (Merging Phase) 与上下文切换，使得并行效率在超过一定核心数后达到平台期。
3. **通信优化无法弥补算力架构错位**：最新的研究尝试通过静态程序结构 (CST) 来优化事件的分发路径，从而减少分析过程中的跨进程通信 (IPC)。然而，这种方法依然受限于 CPU 的 MIMD（多指令多数据）架构。Trace 数据分析的底层逻辑（如海量时间戳比对、简单的算术作差）更契合 GPU 的 SIMT（单指令多线程）架构，强行在 CPU 上进行优化属于算力供给端与负载特征的错位。

### 3.2 CPU-GPU 异构分析管线设计

#### 3.2.1 初始尝试

基于上述剖析，本系统设计了 5 阶段的 CPU-GPU 异构流水线，将 IO、复杂状态维系与高吞吐计算进行解耦：

1. **MPI 并行读取 (CPU)**：利用 `otf2xx` 库在多节点上并行读取 OTF2 文件。采用 Round-Robin 策略分配 Location，并通过单次遍历 (Single-pass) 构建动态数组，最后利用 `MPI_Gatherv` 将所有事件归约至 Rank 0 节点。
2. **P2P 事件匹配 (CPU)**：点对点通信（`MPI_Send`/`MPI_Recv`）的匹配具有严格的时序依赖。在 GPU 上使用哈希表进行匹配容易因线程执行乱序导致时序错乱或探测链断裂。因此，本系统将该步骤保留在 CPU 端，利用时间戳排序的 FIFO 队列进行处理（时间复杂度 $O(N \log N)$），确保 `(sender_rank, receiver_rank, tag)` 的精确双向映射。
3. **集体通信分组 (CPU)**：将离散的集体通信事件（如 `MPI_Barrier`, `MPI_Bcast`）按照时间戳和 Communicator Member Set 重组为完整的逻辑组，为 GPU 计算准备索引。
   1. **GPU 并行分析核心 (GPU)**：将格式化且匹配完毕的 Trace 数据通过 PCIe 传输至 GPU 显存。启动 5 个 CUDA Kernel，并发执行 8 项等待状态分析（Wait-state Analysis）。

4. **统计归约 (CPU)**：GPU 计算完成后，仅将包含有效时延数据的数组传回 CPU，由 CPU 完成后续的均值、方差、分位数（Q25/Q75）等统计学计算。

#### 3.2.2 共享内存优化

 6 阶段的 CPU-GPU 异构流水线，解耦 I/O、状态维系与高吞吐计算：

1. **阶段 1：MPI 并行双趟读取 (CPU)**
   * **Pass 1 (发现)**：各 MPI Rank 分配连续的 Location 块，扫描本地事件并发现通信伙伴（Related locations）。
   * **Pass 2 (加载)**：加载本地及相关事件至 SoA，并将根节点不在本地的集体通信事件通过 `MPI_Gatherv` 重定向至 Root 所在 Rank。
2. **阶段 2：MPI-3 共享内存窗口分配**
   * 利用 `MPI_Win_allocate_shared` 在单节点内实现零拷贝数据共享，使 Rank 0 能够通过指针运算直接访问所有 Rank 的数据，避免大规模点对点通信。结合分布式的 `memset` 与 `madvise(MADV_HUGEPAGE)` 预错页，进一步降低缺页中断成本。
3. **阶段 3：CPU 预处理**
   * **P2P 匹配**：基于时间戳排序的 FIFO 队列进行匹配，确保点对点通信时序的严谨性。
   * **集体通信分组**：利用 FNV-1a 哈希将离散事件重组为 CSR (Compressed Sparse Row) 格式的逻辑组，实现 $O(1)$ 查找。
   * **时间戳修正**：可选的 CLC 补偿机制。
4. **阶段 4：GPU 自适应批处理流分析 (Rank 0)**
   * 根据显存容量动态计算批次大小 $K$。引入 `GPUMemoryPool` 实现一次性内存分配，复用于所有批次。5 个 CUDA 核心并发执行 8 项分析逻辑。
5. **阶段 5：结果收集 (CPU)**
   * 使用 `MPI_Gatherv` 仅收集标量时延数据，而非原始事件。
6. **阶段 6：统计归约 (CPU)**
   * 使用 `std::nth_element` 以 $O(N)$ 复杂度计算各指标的计数、均值、分位数等统计信息。

### 3.3 数据布局重构与显存访存优化

在 CPU 转移到 GPU 的过程中，最大的挑战是“内存墙” (Memory Wall)。由于 GPU 显存容量远小于主机 RAM，且对内存访问模式有严苛要求，本研究彻底重构了底层数据结构：

- **从 AoS 到 SoA 的内存合并 (Memory Coalescing)**：

  传统的 CPU 分析工具通常采用结构体数组 (AoS, Array of Structures) 来存储事件。但在 GPU 中，连续的线程在访问 AoS 时会导致非合并的离散内存事务。本系统设计了 `TraceDataSoA` 结构，将事件类型、时间戳、进程 ID (PID) 等字段完全分离为独立的一维数组。当一个 CUDA Warp (32 个线程) 访问 `timestamps[threadIdx.x]` 时，所有访存请求会落在一个连续的 256-byte 内存块中，从而触发单次合并访问，极大地提高了显存带宽利用率。

- **变长集体通信的 CSR 压缩表示**：

  集体通信涉及的进程数量是动态的（从 2 到数千不等），这与 GPU 偏好定长静态分配的特性相悖。本系统引入了稀疏矩阵计算中常用的压缩稀疏行 (CSR, Compressed Sparse Row) 格式来表征集体通信组。

  通过 `offsets` 数组标记每个组在 `members` 数组中的起始位置，GPU Kernel 只需一次线性寻址即可获取该通信组的所有事件索引。这避免了在显存中维护复杂的指针网络或变长数组。

### 3.4 细粒度并行算法映射与语义对齐

本系统的 8 项分析逻辑被映射为 5 个 CUDA Kernel。针对不同的通信特征，采取了差异化的并行映射策略：

- **网格步长循环 (Grid-Stride Loop) 与原子操作**：

  对于点对点通信（Late Sender / Late Receiver），采用 `kernelLateSenderReceiver` 核心。由于每个事件相对独立，该核心使用一维线程网格，每个线程处理一个 Recv/Irecv 事件。计算结果的存放通过 `atomicAdd` 对全局设备计数器进行自增，以确保高并发下结果数组写入的线程安全。

- **分层规约与 Block 映射**：

  对于集体通信（如 Barrier Wait、Early Reduce），采用 `kernelBarrierWaitCompletion` 等核心。每个 CUDA Block 处理一个集体通信组（Group）。目前的设计中由 Block 的 Thread 0 顺序完成组内最大/最小时间戳的寻找。

- **工业级时间戳语义对齐 (Scalasca Semantics)**：

  为确保计算的科学性，算法在读取和计算阶段严格对齐 Scalasca 的标准。例如，针对非阻塞接收带来的 Late Receiver 误差，算法并没有简单地计算接收和发送点事件的差值，而是分别提取了 Region 的 `Enter(MPI_Irecv)`、`Enter(MPI_Send)` 以及 `Leave(MPI_Send)` 的时间戳。只有满足“发送完成时间晚于接收请求时间”时才被判定为真正的 Late Receiver，消除了 Score-P 插桩探针本身带来的皮秒级系统误差。

## 四、 核心实现细节

### 4.1 SoA 数据布局与显存访存优化
系统将每个事件的约 60 字节数据打散到 14 个连续的独立数组中（如 `events[]`, `timestamps[]`, `srcs[]`, `match_partner[]` 等）。当 GPU 的 32 线程 Warp 访问任一字段时，请求会映射至连续的 128-256 字节内存块，实现完全合并的内存访问 (Coalesced memory access)。

### 4.2 CUDA 分析核心映射语义
* **点对点通信 (P2P)**：采用网格步长循环 (Grid-stride loop)，每个线程处理一个接收事件，通过 `match_partner` 索引直接定位发送事件，并输出至独立数组。
* **集体通信 (Collective)**：每个 CUDA Block 映射一个集体通信组，通过 CSR 格式的索引数组进行线性寻址，避免显存中的复杂指针追踪。

### 4.3 CLC 时间戳近似补偿算法
Scalasca 的受控逻辑时钟 (CLC) 算法需要在所有节点间进行迭代前向和后向摊销。由于集中式架构难以完全复刻，本系统提出了一种“仅限阻塞通信的补偿算法” (Blocking-only neutralization)：
1. 检测匹配的 P2P 事件中是否存在 `send_leave > recv_enter` 的时钟违例。
2. 若违例且为阻塞 `MPI_Recv`，则强制设定 `end_timestamps[i] = send_leave` 以消除伪造的 Late Receiver。
3. 若为非阻塞 `MPI_Irecv`，则保留原值（此时的 Late Receiver 为真实等待）。

## 五、 正确性验证

系统正确性以 Scalasca v2.6.1 作为基准工具进行对比验证。

### 测试结果概览

* **集体通信指标**：在所有 8 个 Trace（LAMMPS 与 NPB CG，16 至 2048 进程）上，6 项集体通信指标（如 Barrier Wait, Early Reduce 等）均与 Scalasca 实现了 **100% 的精确匹配**。
* **总体精确度**：在 72 项测试指标中，69 项实现精确匹配（匹配率 95.8%）。
* **误差分析**：3 项未精确匹配的指标均出现在 LAMMPS 数据集的 `late_receiver` 计数上（开启 `--time-correct`），最大偏差为 0.69% (LAMMPS 1024 进程)。根本原因在于分布式双趟读取将接收端的时间线跨 Rank 拆分，导致本系统的近似 CLC 算法未能捕获 Scalasca 全局 CLC 所能修正的极少数边缘时钟违例。

## 六、 已知局限性与后续研发计划

当前系统在逻辑构建上已趋于完善，但在极端扩展性与功能完备性上仍存在以下问题，并构成下一阶段的核心工作：

### 6.1 已知缺陷与局限
1. **整数溢出导致的大规模崩溃**：在处理包含 4096 及以上进程的 Trace (如 NPB CG 4096) 时，集体通信的 `MPI_Gatherv` 偏移量计算发生 32 位整型溢出，触发 `std::length_error` 导致程序崩溃。此问题直接阻碍了工具向更大规模扩展。
2. **分析语义缺失**：尚未实现 Scalasca 定义中的第 9 个分析指标——针对 Scan/Exscan 的 `early_scan`。
3. **I/O 与单节点瓶颈**：OTF2 的单线程回调读取架构占据了管线 67%-97% 的总时间。且所有 MPI Reader 目前限制在单一物理节点内。

### 6.2 演进计划 (Future Work)

* **短期修复**：将所有涉及 `MPI_Gatherv` 与通信域去重的位移计算类型由 `int` 重构为 `int64_t`，解除 4096+ 进程的扩展限制，并补充实现 `early_scan` 算法逻辑。
* **中期架构演进**：引入跨节点分布式读取 (Multi-node distributed reading)，利用多个计算节点执行高并发 I/O 吞吐，最终通过网络汇聚至单 GPU 节点进行计算，结合两种架构的优势。
* **长期研究**：探索将 Trace 数据进行 One-time 格式转换，构建 GPU 友好的原生二进制 SoA 格式，从而彻底绕过 OTF2 库繁重的解析开销。
