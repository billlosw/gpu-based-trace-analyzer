# GPU Trace Analyzer - Project Overview

## What This Project Does

This project is a **CUDA-accelerated MPI trace analyzer** that reads OTF2 trace files generated by Score-P-instrumented MPI programs, and computes 8 wait-state metrics that identify performance bottlenecks in MPI communication patterns. These are the same metrics produced by the industry-standard tool **Scalasca** and by the CPU-based reference implementation **TileTrace**.

The key idea: replace TileTrace's multi-node CPU-based parallel analysis with a single-GPU approach that uses CUDA kernels for parallel event processing, while using MPI only for accelerating I/O (parallel trace reading).

## The 8 Wait-State Analyses

| # | Analysis | What It Measures | Applies To |
|---|----------|------------------|------------|
| 1 | **Late Sender** | Sender started MPI_Send after receiver started waiting (MPI_Recv/MPI_Wait) | Point-to-point |
| 2 | **Late Receiver** | Receiver started waiting after sender started MPI_Send | Point-to-point |
| 3 | **Barrier Wait** | Time each process waited for the slowest to arrive at MPI_Barrier | Barrier collectives |
| 4 | **Barrier Completion** | Time imbalance in how processes exit MPI_Barrier | Barrier collectives |
| 5 | **Early Reduce** | Root arrived early relative to slowest member in Reduce/Gather | Root-based collectives |
| 6 | **Late Broadcast** | Root arrived late relative to early-arriving members in Bcast/Scatter | Root-based collectives |
| 7 | **Wait NxN** | Same as barrier wait but for AllReduce, AlltoAll, AllGather, etc. | N-to-N collectives |
| 8 | **NxN Completion** | Same as barrier completion but for N-to-N collectives | N-to-N collectives |

## Processing Pipeline

```
                          +-----------------------+
                          |  OTF2 Trace File      |
                          |  (.otf2 + traces/)    |
                          +-----------+-----------+
                                      |
                    Step 1: MPI-Parallel Reading
                    (N ranks, round-robin locations)
                                      |
                          +-----------v-----------+
                          | MPI_Gatherv to rank 0 |
                          | SoA data in host RAM  |
                          +-----------+-----------+
                                      |
            +-------------------------+-------------------------+
            |                                                   |
   Step 2: P2P Matching (CPU)                    Step 3: Collective Grouping (CPU)
   timestamp-sorted FIFO queues                  comm_set-based, produces CSR
            |                                                   |
            +-------------------------+-------------------------+
                                      |
                    Step 4: cudaMemcpy Host -> Device
                                      |
                          +-----------v-----------+
                          |  5 CUDA Kernels       |
                          |  (8 analyses total)   |
                          +-----------+-----------+
                                      |
                    Step 5: cudaMemcpy Device -> Host
                                      |
                          +-----------v-----------+
                          | CPU Statistics        |
                          | (sort, quartiles)     |
                          +-----------+-----------+
                                      |
                          +-----------v-----------+
                          |   Formatted Output    |
                          |   (stdout)            |
                          +-----------------------+
```

## Key Design Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Data layout | **SoA** (Structure of Arrays) | GPU coalesced memory access; warps read contiguous addresses |
| Trace reading | **MPI-parallel**, otf2xx | Dominated by I/O; parallelizing across ranks gives near-linear speedup |
| P2P matching | **CPU**, timestamp-sorted FIFO | Requires temporal ordering which is hard to do correctly on GPU with atomics |
| Collective grouping | **CPU**, comm_set-based CSR | Variable-length groups; small fraction of total events; produces GPU-friendly CSR |
| Analysis kernels | **GPU CUDA kernels** | Massively parallel event processing; one thread/event for P2P, one block/group for collectives |
| Event linking | **Index-based** (int32_t) | GPU-compatible; no pointers across host/device |

## Comparison with TileTrace

| Aspect | TileTrace (CPU) | GPU Analyzer |
|--------|-----------------|--------------|
| Parallelism | MPI across nodes | MPI for I/O only, CUDA for analysis |
| Data Layout | AoS (struct Event) | SoA (12 contiguous arrays) |
| P2P Matching | CPU hash map during replay | CPU timestamp-sorted FIFO queues |
| Collective Groups | Inline with matching | Separate CPU preprocessing -> CSR |
| Reading | Serial or MPI (1-pass per rank) | MPI-parallel (round-robin locations) |
| Hardware | 2x Xeon Gold 6530, 1TB RAM | 1x RTX 4090/5090 + any CPU |

## Validation Status

7 of 8 analyses **match Scalasca exactly** (count and sum within 1 picosecond of floating point rounding):
- late_sender, barrier_wait, barrier_completion, early_reduce, late_broadcast, wait_nxn, nxn_completion

The remaining analysis (**late_receiver**) over-counts because the tool classifies ALL pairs where `recv_enter > send_enter` as late_receiver, while Scalasca only counts pairs where the MPI call actually blocked (nonzero wait state). See [ANALYSIS-DETAILS.md](./03-ANALYSIS-DETAILS.md) for full explanation.
